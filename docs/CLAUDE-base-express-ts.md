## Структура

```
src/
  index.ts          точка входа: сборка приложения и listen
  app.ts            конфигурация Express без listen (нужно для тестов)
  config/env.ts     Zod-схема переменных окружения
  routes/           только HTTP: парсинг запроса, вызов сервиса, формирование ответа
  services/         бизнес-логика, ничего не знает об Express
  repositories/     доступ к данным, ничего не знает о бизнес-правилах
  middleware/       auth, rate limit, обработчик ошибок, request-id
  utils/
  types/
```

## Правила кода

### TypeScript

- `strict: true`. `any` запрещён — используй `unknown` с сужением типа.
- Никаких `@ts-ignore` без комментария с объяснением на той же строке.
- Типы для внешних данных выводятся из Zod-схем через `z.infer`, а не пишутся руками отдельно.
- Экспортируй типы рядом с кодом, который их использует, а не в общую свалку `types.ts`.
- ESM (`"type": "module"`), импорты с расширением `.js` в скомпилированном виде.

### Слои

- Роут не содержит бизнес-логики. Максимум: валидация входа, вызов сервиса, маппинг результата в HTTP-ответ.
- Сервис не импортирует ничего из `express` — ни `Request`, ни `Response`. Это делает логику тестируемой без поднятия сервера.
- Репозиторий не содержит условий бизнес-правил.
- Зависимости передаются аргументами или через конструктор, а не импортируются как синглтоны — иначе их не подменить в тестах.

### Express

- Все асинхронные хендлеры обёрнуты в `asyncHandler`, иначе отклонённый промис не дойдёт до обработчика ошибок.
- Обработчик ошибок — последний `app.use` с четырьмя аргументами.
- Валидация входа — Zod-middleware на `body`, `query`, `params`. Невалидированные данные в сервис не попадают.
- Обязательный набор middleware: `helmet`, `cors` с явным списком origin, `express.json({ limit })`, rate limit, request-id.
- `/healthz` возвращает статус процесса и пинг зависимостей.
- Graceful shutdown на `SIGTERM`: перестать принимать соединения, дождаться текущих, закрыть пул БД.

### Ошибки

- Свой класс `AppError` с полями `statusCode`, `code`, `isOperational`.
- Клиенту — только `code` и человекопонятное сообщение. Никаких stack trace и текстов ошибок БД наружу.
- В лог — полная картина с `requestId` и, если есть, `userId`.
- Неожиданные исключения (`isOperational: false`) логируются как `fatal`.

### Логи

- Только Pino, структурированный JSON. Никаких `console.log` в `src/`.
- Секреты, токены, пароли и содержимое `Authorization` не логируются никогда — настрой `redact` в конфиге Pino.
- Каждый лог внутри обработки запроса несёт `requestId`.

### Конфигурация

- Все переменные окружения объявлены в Zod-схеме `config/env.ts` и валидируются при старте. Не хватает переменной — процесс падает с понятным сообщением, а не ломается в рантайме.
- `process.env` читается только в этом файле. Везде остальном — импорт готового типизированного объекта.
- `.env.example` содержит все переменные с комментариями и обновляется вместе с кодом.

### Тесты

- Vitest. Unit-тесты для сервисов и утилит, интеграционные для роутов через `supertest` поверх `app.ts`.
- Внешние HTTP-вызовы всегда замоканы. Тесты не ходят в сеть.
- Тест называется по проверяемому поведению, а не по имени функции.
- Каждый баг-фикс сопровождается тестом, который падал бы до исправления.

### Безопасность

- Секреты не коммитятся. `.env` в `.gitignore`.
- Параметризованные запросы, никакой конкатенации SQL.
- Rate limiting на все публичные эндпоинты.
- Зависимости добавляются только если действительно нужны — каждая новая это поверхность атаки.

## Как работать над задачей

1. Прочитай существующий код рядом с местом изменения, прежде чем писать новый — следуй сложившимся в проекте конвенциям, а не своим привычкам.
2. Крупную задачу разбей на этапы и покажи план до начала реализации.
3. Меняй минимум необходимого. Не рефактори соседний код заодно, если об этом не просили.
4. Не добавляй библиотеку без объяснения, почему не хватило существующих.
5. Не пиши комментарии, пересказывающие код. Комментарий объясняет «почему», а не «что».
6. Если требование в задаче противоречит этому файлу — остановись и спроси, а не выбирай молча.

## Чего не делать

- Не создавать `README`, `CHANGELOG` и прочие файлы документации, если не просили.
- Не коммитить и не пушить без явной просьбы.
- Не менять конфиги сборки, линтера и CI ради обхода ошибки — чинить причину.
- Не отключать правила линтера точечными подавлениями без объяснения.
